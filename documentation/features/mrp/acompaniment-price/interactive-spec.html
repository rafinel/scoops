Context and scope

One Manager-reviewed product price, shared across all linked Portions and sizes.

Spec revision 3 · Completed

Objective

Managers configure an Accompaniment sale price through a Portion’s Link/Edit dialog. Future sales use that price; a price change during cart assembly requires renewed confirmation.

Current gap

MRP currently has no Accompaniment sale price. Linked tables show “Não disponível”, Link/Edit omit price, and PDV derives the commercial price from acquisition cost and consumption quantity.

Included

  • Shared product price, validation, role and establishment boundaries.
  • First-save Resale proposal, atomic Link/Edit saves and category compatibility.
  • Migration without backfill, PDV repricing and immutable order snapshots.

Excluded

  • Dedicated Accompaniment Prices page or field.
  • Per-link, per-type, per-Portion or per-size price overrides.
  • Payment or inventory-consumption rule changes.
  • History rewrites, category remediation or rollout preflight.
Confirmed product decisions

Q1 accepted Manager-reviewed first-price initialization; Q2 rejected new Portion+Accompaniment combinations; Q3 required a dedicated Pencil PDV review state; Q4 declined rollout preflight; Q5 removed the Accompaniment-only Prices tab; Q6 allowed shared-price edits in Link/Edit and Operator inspection in linked tables; Q7 limited Accompaniment pricing to Link/Edit even for Accompaniment+Resale. The user confirmed the consolidated contract. Unpriced legacy links are unavailable to future PDV selection until a Manager saves a price. A saved price remains on the product after its last link is removed and can be reused in a later Link action.

Ownership and source

MRP owns product pricing; PDV consumes commercial facts and owns order confirmation and snapshots. Issue #56 is refined by the confirmed decisions recorded in the Spec.

All functional requirements · FR-01–FR-10
FR-01 · MRP PRQ-01

New link creation and category changes reject Portion+Accompaniment together. Accompaniment+Resale remains valid. An existing link remains editable when its retained target has both Portion and Accompaniment categories, provided Accompaniment is still present. Existing product categories are not automatically rewritten.

FR-02 · MRP PRQ-05, PRQ-09

Accompaniment alone adds no Prices tab. Accompaniment+Resale retains its Resale Prices page without an Accompaniment price field. Managers configure Accompaniment price only through Link/Edit; Operators inspect it read-only in linked Portion tables.

FR-03 · MRP PRQ-08, PRQ-09

One price belongs to the Accompaniment product, separate from acquisition cost and Resale price. It is finite, non-negative, has at most two decimal places, and is below 10^16 so it fits numeric(18,2) as a JavaScript number; the largest accepted value is 9_999_999_999_999_998. Unset differs from zero; zero means free.

FR-04 · MRP PRQ-08, PRQ-09

Link/Edit prefill the saved price. Before first save, propose the configured Single Resale price or current main brand's configured By-brand Resale price, if available. Otherwise require entry. Opening/closing a dialog writes nothing; after save, Resale/main-brand changes do not synchronize this price.

FR-05 · MRP PRQ-08, PRQ-09

A first link requires a valid saved or entered price. Saving an entered/edited price and a new or edited link is atomic, including affected commercial publication. Failure/cancel preserves data and usable editing context.

FR-06 · MRP PRQ-08, PRQ-09

Every table/link/Portion size uses the same current product price. Quantity, type and brand cost do not scale it. Cost preview stays separate. Either Link/Edit price change updates future commercial facts for every affected Portion.

FR-07 · MRP PRQ-09, PDV PRQ-03

PDV uses the saved product price once per selected accompaniment per Portion, independent of stock consumption quantity or size. An unconfigured price cannot become zero or saleable. Zero displays `Grátis` and remains zero under channel adjustment.

FR-08 · PDV PRQ-07

Registration revalidates current prices. A changed price preserves/recalculates the cart, displays affected item and total values, and requires review followed by new explicit confirmation. Another concurrent change requires review again.

FR-09 · MRP PRQ-09, PDV PRQ-09

Price changes affect future sales. Registered order snapshots retain their captured accompaniment base/final prices, item values and total.

FR-10 · MRP PRQ-05, PRQ-08, PRQ-09

Price reads/writes enforce establishment scope and current product eligibility. Only Managers mutate; Operators have no edit actions. Rejections and persistence/publication failures cannot partially update price, link, order or stock.

// Imports used by the method in the existing use-case file:
import type { Product } from '#mrp/domain/entities/product.ts'
import type { MrpDatabaseRepositories } from '#mrp/interfaces/mrp-database.ts'
import { BadRequestError } from '#shared/domain/errors/index.ts'

// Class member; not a loose function and not a Product method.
private async saveAccompanimentPrice(
  scope: MrpDatabaseRepositories,
  target: Product,
  suppliedPrice: number | undefined,
): Promise<Product> {
  if (suppliedPrice === undefined) {
    if (target.accompanimentPrice === undefined) {
      throw new BadRequestError('Informe o preço de venda do acompanhamento.')
    }
    return target
  }

  if (
    !Number.isFinite(suppliedPrice) ||
    suppliedPrice < 0 ||
    Number(suppliedPrice.toFixed(2)) !== suppliedPrice
  ) {
    throw new BadRequestError(
      'O preço deve ser maior ou igual a zero e ter até duas casas decimais.',
    )
  }

  return scope.productsRepository.replace(target.establishmentId, target.id, {
    accompanimentPrice: suppliedPrice,
  })
}

The price method is invoked with the freshly loaded target and request.input.accompanimentPrice. Do not use truthiness (if (price)) because zero is intentional. Do not convert omitted input to zero or persist the displayed suggestion. Do not open a second transaction or invoke a broker. Repository replace(establishmentId, productId, changes) is the existing tenant-aware overload; include only the changed accompaniment field so price writes do not overwrite unrelated Product state.

Transactional order is: authorize and validate request → enter MrpDatabase.run → load/check owner/link/target/type/current price → optionally save target price → add/replace link → read fresh output and affected facts → add typed events → return from transaction. If any repository, fact-building or event insert fails, Product/link/outbox changes all roll back. Existing serializable MRP semantics govern competing intentional writes; no new CAS field, automatic application retry or lock-order protocol is introduced. For price changes discover inverse owners from the target ID, otherwise only publishing with owner ID misses other linked Portions.
