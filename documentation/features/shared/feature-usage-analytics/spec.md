# Feature usage and workflow analytics

## 1. Context and scope

**Objective:** Let the Scoops team measure feature adoption and workflow friction through PostHog without interrupting customer workflows or collecting their entered data.

**Source and depth:** [Issue #51](https://github.com/rafinel/scoops/issues/51), **complete**: browser identity lifecycle, persistent anonymous correlation, multiple module consumers, an external SDK, deployment configuration, privacy, and browser SDK validation.

**Baseline and gap:** Web currently wraps Better Auth and Sentry through provision adapters, resolves a Scoops account before granting authenticated UI context, and exposes onboarding, catalog, manual stock, and production consumers. It has no PostHog dependency or product-usage instrumentation. Existing Sentry signals do not define product adoption or conversion.

**Approved source deviations:** In this chat, the user expanded the issue's initially excluded operational instrumentation to **manual stock entry/write-off and production**. The user subsequently replaced custom/versioned dashboard tooling with **native PostHog insights configured through its UI**. The consolidated contract and Architecture addition were confirmed on 2026-10-05. The user subsequently removed remote staging/reporting acceptance and redundant manual checkers. The original issue remains the source; these decisions override its narrower workflow scope and dashboard/reporting delivery wording.

**Included:** Authorized main feature visits; anonymous onboarding and confirmation; authenticated product creation, manual stock entry/write-off, and production; field-only invalid submissions, blocking episodes, safe failure codes, elapsed durations; event instrumentation and native funnel, trends, and retention setup documentation.

**Excluded:** Backend/SSR tracking, authoritative business/audit records, customer-facing analytics UI, additional workflow instrumentation (including brand CRUD, recipe editing, invitations, order creation/cancellation, discounts, and sales-channel management), custom dashboard construction, custom queries, dashboard definitions/provisioning scripts, PostHog group analytics, remote staging ingestion verification, configuring/saving native insights, time-spanning retention fixtures, new business APIs/migrations, new production deployment automation, and any change to Sentry recording. Page visits to permitted destinations remain included even when their action workflows are excluded. This Spec does not repair unrelated pre-existing business discrepancies or strengthen mutation request guards solely for analytics.

**Decisions:** Starts occur at fresh form/dialog entry, not first interaction; restored pending onboarding continues its occurrence. Other forms/dialogs begin a new occurrence after leaving and reopening. Anonymous identity and safe onboarding timing may survive browser restarts, but cannot restore application sessions or entered values. Duration is elapsed time including waiting/retries. The onboarding funnel window is seven days. Weekly metrics use Monday-start calendar weeks in `America/Sao_Paulo`. Staging and production use separate projects; collection is disabled until explicitly configured. Acceptance is based on permitted consumer tests and intercepted browser SDK transport. Remote ingestion/person merging and native reporting results are not verified by this delivery; project access is not an implementation prerequisite.

**Revision 2 amendment:** The user approved separate workflow payload schemas composed from a shared envelope and selected through a discriminated union keyed by `workflow`. This makes the existing event/field/phase constraints enforceable without changing event names, measured workflows, entered-value exclusions or customer behavior. No implementation/Evaluation evidence exists to mark historical.

**Revision 3 amendment:** The user requires an explicit shared analytics context and named consumer hook rather than leaving distribution of the provider contract open. This clarifies composition and lifecycle ownership without changing collection scope, event schemas or reporting semantics. No implementation/Evaluation evidence exists to mark historical.

**Revision 4 decisions (Q12–Q18):** The adapter owns analytics occurrence/attempt/timing/deduplication state behind explicit operations. Drop responses after the initiating identity changes. Defer an initial workflow start until safe identity reconciliation, retaining its entry time; do not queue other application events. Keep PostHog's bounded in-memory retries, with no application retry or persistent event queue. Invalid enabled deployed configuration fails the build. Match restored onboarding timing through an opaque marker added to the existing onboarding envelope. Cross-tab logout/account changes invalidate peer analytics until each peer independently resolves fresh auth state; do not force an auth refresh. The retry choice supersedes Q14's initially accepted zero-transport-retry recommendation after SDK research established that it is incompatible with normal SDK capture/identify. No implementation/Evaluation evidence exists to mark historical.

## 3. Technical Contract

### Ownership and existing boundaries

Shared `packages/core/src/shared/interfaces` owns the provider-neutral technical capability; serializable shared values belong to its existing domain-structures boundary and public subpath barrels. No PostHog, React, environment, browser global or Zod dependency enters Core. This is not an Analytics business use case or a persisted domain event.

`apps/web/src/provision` owns a configured browser singleton client and an owning provider factory with an optional client dependency, as Provision Rules require. Third-party calls, sanitization and provider/storage failure containment stay in provision, not widgets, contexts or REST services. The required shared analytics context distributes the contract; owning module widget/action consumers supply observations through its named consumer hook. The public context/hook and their composition are specified below; remaining internal decomposition stays implementer-owned.

### Shared analytics context

Require `AnalyticsContextProvider` under `apps/web/src/ui/shared/contexts/analytics-context/` and the public `useAnalyticsContext` consumer hook under `apps/web/src/ui/shared/hooks/`. Follow the repository context directory convention: the context entry point owns a null-initialized context and declarative provider; `AnalyticsContextValue` belongs in its types boundary; the colocated `useAnalyticsContextProvider` owns construction, React effects, derived availability/identity and subscription lifecycle. Only `useAnalyticsContext` imports/reads the raw context; widgets, page/action hooks and layouts use that consumer hook. Its missing-context guard follows the existing UI `AppError` convention.

Mount one `AnalyticsContextProvider` in `RootLayout`, inside the existing `AuthContextProvider` and above all public/authenticated page consumers, so it can consume resolved auth state through `useAuthContext`. Do not mount it only in authenticated `AppLayout`, create module-specific copies, or turn it into a route-remounting provider. Keep the existing Query/Auth/REST provider responsibilities and Sentry initialization intact. Disabled analytics still mounts this context and supplies the no-op provider contract; normal application composition never omits the context because collection is disabled.

The context value exposes the typed operations below, not an unrestricted event-name/properties `capture`, PostHog client, SDK types, arbitrary SDK options or raw auth session. Identity coordination belongs to `useAnalyticsContextProvider`: observe the existing auth context, then delegate identity reconciliation/suspension to the analytics adapter under the established identity contract. Navigation observation uses the same shared context operations; the hook owns React subscription cleanup, with one active lifecycle and StrictMode/rerender-safe occurrence semantics. Do not add a second router-level capture path alongside context-owned observation.

Keep form/dialog state and submission triggers in their existing owning hooks. Context lifecycle coordinates shared availability/authentication and distributes analytics dependencies; it does not own business policy, perform REST operations, evaluate stock/production eligibility, serialize registration storage or call the SDK. Adapter-owned schema parsing, privacy filtering, browser storage/time and nonblocking failure containment remain in provision. The context consumes their outcomes without telemetry-error toasts or interrupted user actions. Verify context behavior through permitted root/app-layout and browser consumers, not dedicated analytics-context/provider/shared-hook tests; do not change the test-integrity allowlist for this amendment.

### Public operations and analytics state ownership

Name the neutral Core interface `ProductTelemetryProvider` to distinguish shared product telemetry from customer Analytics-module providers. Its consumer-facing methods form `AnalyticsContextValue`. All operations return synchronously, contain telemetry failures, and never return a transport promise or determine whether a business request may proceed. Disabled/unavailable collection returns inert handles with the same shape, so callers need no telemetry availability branch.

`WorkflowHandle` and `AttemptHandle` are opaque Core values, unrelated to resource IDs or authentication tokens. `WorkflowHandle` exposes only a readonly `occurrenceId` (undefined for an inert handle) so the owning onboarding consumer can save the approved optional marker; all state/counters/context remain private to the adapter. The adapter creates the workflow ID, captures entry time, increments attempts, snapshots initiating identity, and owns completed-event/block/deduplication state. UI consumers retain handles but never calculate counters/durations or manufacture account context. Inputs and handles are strict-validated; malformed inputs are dropped before any SDK capture.

| Consumer operation | Input and synchronous result | Required state/event effect |
| --- | --- | --- |
| `startWorkflow` | `{ workflow, entryKey, restoredOccurrenceId? }` → `WorkflowHandle` | `entryKey` is a caller-owned opaque token stable for one actual form/dialog entry, never a route/resource ID. Same key during rerender/StrictMode replay returns the same handle and emits no second start. A new entry creates one ID/time and emits the appropriate specialized or operational start. A restored onboarding marker reopens validated pending state without another start. No other workflow accepts restoration. |
| `startAttempt` | `{ workflow: WorkflowHandle }` → `AttemptHandle` | Increment the workflow's positive attempt number once per actual invalid submit or dispatched mutation request. Call at that boundary, not button render, query invalidation or automatic retry of analytics transport. The same returned handle accompanies validation or the API outcome; every actual new business request gets a new handle. |
| `recordValidationFailure` | `{ attempt: AttemptHandle, fields }` → `void` | Emit once for this invalid submission with normalized allowed field labels. No messages/values. Production disabled-input states use `recordBlock`, not an invented invalid submit. |
| `recordBlock` | `{ workflow: WorkflowHandle, block: null \| { phase, failureCode, fields } }` → `void` | Non-null is supplied only after relevant input and a real block. Compare normalized sorted field/reason/phase sets; emit once per episode. Null denotes recovery and clears the episode. Pending requests and untouched defaults do not create or clear a real blocking episode by themselves. |
| `recordFailure` | Submission: `{ attempt: AttemptHandle, phase: 'submission', failureCode, statusClass? }`; preview: `{ workflow: WorkflowHandle, observationKey, phase: 'preview', failureCode, statusClass? }` → `void` | Emit once per failed business request/preview observation, under the exact variant matrix. Failed submission does not end the workflow; a real retry gets another attempt. `observationKey` identifies an actual preview request, not its returned business data. |
| `completeWorkflow` | Operational: `{ attempt: AttemptHandle }`; onboarding registration: `{ attempt: AttemptHandle, onboardingExpiresAt }` → `void` | Emit once on that request's successful mutation response with adapter-calculated elapsed time. `onboardingExpiresAt` is the safe original API deadline in epoch milliseconds, not entered data; persist it with start/marker after validating the pending response. Operational success closes the occurrence for new attempts but does not hide another actual concurrent request's distinct outcome. For onboarding, emit registration completion and retain pending timing until terminal confirmation/expiry/restart. |
| `endWorkflow` | `{ workflow: WorkflowHandle }` → `void` | Actual exit/cancel/restart ends the occurrence without a completion event. Cleanup cancels unsent deferred starts and releases active state. An already dispatched business request may still report its own outcome if its initiating identity remains current. StrictMode effect replay alone is not a new entry or an actual cancel. |
| `recordEmailConfirmation` | `{ observationKey, workflow?: WorkflowHandle, outcome: 'success' \| 'failure', failureCode?, statusClass? }` → `void` | Actual confirmation request gets an opaque observation key. Success emits `email_confirmation_completed`; failure emits the automatic-confirmation submission variant. No submit attempt is invented. Use correlation/time only when a validated pending marker is available. Success captures duration then clears obsolete persisted pending timing. |
| `recordAccountActivationFailure` | `{ observationKey, workflow?: WorkflowHandle, failureCode, statusClass? }` → `void` | Emit the distinct `account_activation` failure after successful confirmation when existing activation fails. Retain a safe in-memory confirmation reference for this callback; no pending token or completed timing record is restored. |
| `recordFeatureVisit` | `{ feature, entryKey }` → `void` | Called by the authorized navigation observer, with a stable key for that resolved destination entry; emit once under current resolved account context. A genuine revisit gets a new key; search/hash/filter changes do not. |

Provider lifecycle methods are not widget APIs: `reconcileIdentity` consumes the existing resolved auth state, `suspend` invalidates emission until reconciliation, and `dispose` cleans subscriptions and active local analytics state without awaiting transport. Only the context provider hook uses these methods. Clock, storage, SDK client and same-origin notification dependencies belong to the owning provision factory; use production defaults with injectable dependencies as permitted by Provision Rules.

Before initial safe identity reconciliation, retain only the active workflow's ID, original entry time and entry key, not queued event bodies. Emit its start when safe reconciliation finishes only if that entry is still active. If it ends or identity cannot be reconciled, discard the unsent start. Other early observations are dropped; later events are never replayed as a fabricated success. Initial waiting never delays UI or business requests. Temporary suspension does not start another occurrence or retry an already sent event.

### Observation and event schema

| `onboarding_started` | Fresh onboarding form occurrence; `workflow: onboarding`, `workflow_id` |
| `onboarding_registration_completed` | Successful initial registration API result; `workflow: onboarding`, `workflow_id`, `attempt`, `duration_ms` when known |

No product, brand, ingredient, registration-token or session-token identifier is required in analytics. Correlation identifiers are analytics-generated opaque values unrelated to authentication or resource IDs.

### Workflow-specific runtime schemas

Reusable telemetry payload validation belongs in `@scoops/validation`, under its Web concern, independently of the existing business/form schemas. Define one public schema for each of `onboarding`, `product_creation`, `stock_entry`, `stock_write_off` and `production`. Compose shared envelope/metadata primitives rather than copying them into each schema; stock entry and write-off may reuse stock field primitives while retaining separate literal workflow branches. A workflow-discriminated union composes these five schemas; each branch further constrains its event variants. Feature visits and required SDK identity-linkage events use separate strict shapes, not a fabricated workflow. Internal declaration/file names remain implementer-owned; follow one primary reusable schema per file and Validation root exports.

The logical validation candidate includes the event-name discriminator and the `workflow` discriminator for workflow observations. Export `workflow: onboarding` on specialized onboarding events as well; it is not only an internal discriminator. Capture uses the event names in the table above. Submission attempts are positive integers; durations are finite nonnegative numbers; schema/environment/discriminator values are closed sets. Establishment and role context is paired when present, and role validation derives from the existing Core `UserProfile`, not a duplicated enum. Anonymous onboarding remains valid without account context; operational events require authenticated establishment/role context.

Every event requires `schema_version` and `environment`. The SDK attaches `distinct_id` after safe identity reconciliation. The following application-property matrix is exhaustive: **all properties not listed for a row are forbidden**; attempt/phase/field/failure properties are permitted only where explicitly listed. ### Identity, occurrences and elapsed time

1. Anonymous onboarding uses persistent analytics identity distinct from auth. SDK identification after resolved `Account` must link that anonymous identity with `Account.id`; retain the minimum SDK `$identify` linkage needed for merged-person queries. Do not implement aliasing from tokens/email or merge different authenticated users. Registration/confirmation API completion can be captured anonymously before account resolution; subsequent identify stitches the same-browser history.
2. No authenticated protected event is emitted while account/access is unresolved or unavailable. Clear event context when account disappears; definitive anonymous/expired/denied/sign-out state resets identified SDK context even if remote sign-out fails. Temporary account resolution suspends emission without repeatedly creating anonymous people. Account changes reset the former identity before identifying the new one; role/establishment updates apply to later events from resolved account state. Each dispatched request snapshots the current local identity generation. Drop its observation if that generation is no longer current at response time, including known logout/account switch or peer invalidation; never preserve it under the old identity or reattribute it to the new one. Ordinary same-person account refresh need not change generation, but emission waits for resolved access. For an unchanged identity generation, capture with currently resolved event-time establishment/role, then freeze that context for SDK retries. No unresolved protected event is queued.
3. Onboarding has one correlation/start time per actual application attempt. Add only a nonsecret analytics occurrence marker to the existing versioned Identity onboarding-session envelope; do not add a server registration ID or alter token/session semantics. The owning UI consumer passes that marker, never the envelope/token/form values, to the adapter. The adapter stores its own safe timing record keyed by the same marker. Pending restoration must first validate the application envelope and successfully refresh pending status; reuse timing only if the marker matches, the safe record is valid, and the original deadline has not elapsed. Missing/mismatched/corrupt records or legacy envelopes without the optional marker restore existing product behavior but omit unknown correlation/duration rather than invent a fresh onboarding start. Failure to write analytics metadata cannot fail registration/restoration. Correction/resend preserve the marker and original start/deadline. Restart/expiration/terminal confirmation clear the marker and associated obsolete timing; initial registration completion does **not** clear confirmation-wait timing. Safe timing can survive browser restarts only when the application independently restores the matching attempt. Analytics never recreates a pending session or entered form values. Never hash tokens, email or names into a correlation value.
4. Product/stock/production workflows live for one entered form/dialog occurrence. Leaving/cancelling ends it without a completion fact; reopening, including a fresh form after reload, starts another. Each actual submission has an occurrence/attempt identity; an invalid submit or API retry is another attempt in the same open workflow. Duplicate suppression is scoped to the same event occurrence/request, not event name, lifetime route, account or product. Preserve existing mutation behavior; multiple actual requests must not be hidden as one event.
5. API-success observation happens immediately on successful response, before awaited query invalidation, UI callbacks or navigation. A later UI failure cannot remove that observation or become an API submission failure. Confirmation API success and account activation failure are separate phases. Production preview requests never produce completion. Capture callbacks do not wait for telemetry transport.
6. Duration is elapsed milliseconds from the workflow's entry to its API success, including retries, hidden-tab time and email waiting. Restore persisted onboarding timing only within its seven-day lifecycle; omit unknown, expired, negative/nonfinite or corrupt timing instead of fabricating zero. Provider-owned time/storage access keeps tests deterministic. Do not await analytics on cancel/close/unmount. Browser timing is not an authoritative SLA or business timestamp.

### Tab isolation and cross-tab invalidation

Keep authenticated SDK identity, resolved establishment/role, operational workflow handles and request identity generations in tab-local memory. Bootstrap anonymous SDK identity from an application-owned opaque anonymous ID in local storage; do not persist authenticated SDK identity, cookies or event bodies. When a seed first links to an account, rotate the persisted seed for future anonymous initialization and invalidate peers that might still use the linked seed; keep the current tab's safely identified account in memory. Definitive auth end/account switch also rotates the anonymous seed before another person can reuse it. Same-person refresh is not another merge/reset.

The adapter publishes an opaque generation/invalidation marker to same-origin peers when it observes definitive auth end or account switch. Notifications contain no account ID, role, establishment, token or form data. Peers immediately suspend emission and invalidate their old request generations; they do not identify themselves from the notification or force a business/auth refresh. Resume only after that peer's existing auth lifecycle independently obtains fresh resolved state **after** invalidation. A previously cached resolved account is insufficient. If no ordinary refresh occurs, remain suppressed until normal reload/restoration. Receiving a notification does not rebroadcast it or rotate identity again; deduplicate the same marker to avoid loops. If browser messaging is unavailable, use an opaque local-storage change signal; storage/messaging denial leaves collection conservative and records cross-tab continuity limitations.

Known transitions are observed through existing auth lifecycle facts; this does not promise immediate detection of a cookie changed externally without a Scoops notification. Multiple tabs may share the anonymous seed or copy a session envelope; each tab's deduplication is local. Do not claim cross-tab exactly-once onboarding observation or authoritative auth synchronization. Remove task-owned listeners on provider teardown; no polling, background server calls or SDK-driven account refresh is introduced.
